Arranca el módulo de Agentes

El módulo de agentes se desarrolla a lo largo de tres sprints (S11–13). La pregunta central de este primero: si ya sé responder con RAG en una llamada, ¿cómo planifico en varios pasos con estado y control? Aquí ves los fundamentos: el ciclo, el estado y la parada.

Del RAG de S10 al agente de S11

S10  pregunta → responder()       → una respuesta (+ fuentes)
 ↓
S11  mensaje  → procesar_turno() → conversación + AgentState → resultado
 ↓
S12+ el agente pasa a actuar con herramientas (en preparación)
Idea que atraviesa el sprint Un agente, en lo esencial, es loop + estado + parada + LLM. El LLM propone datos estructurados; Python decide done y los límites. El resto (tools, RAG, LangGraph) son capas que llegan después.
1

Qué es un agente

Agente = sistema que, ante un pedido, ejecuta varios pasos de razonamiento, actualiza un estado y para cuando cumple el objetivo o un límite. Sirve para tareas que no se resuelven bien con una sola llamada al modelo.

LLM, chatbot, asistente, RAG y agente

ConceptoQué hace¿Estado de tarea?¿Varios pasos?
LLMGenera o completa textoSolo lo del promptNo por sí solo
ChatbotConversación turno a turnoHistorial de mensajesNo planifica una tarea
AsistenteAyuda con un rol fijoA veces (perfil)Suele ser 1 respuesta/turno
Pipeline RAGRecupera y genera una respuestaNo multi-pasoFlujo fijo (recuperar→generar)
AgenteRazona, actualiza estado, decide seguir/pararSíSí (loop + parada)
Un chat con historial NO es un agente Si cada mensaje dispara una sola pasada fija (p. ej. un RAG), no hay un objeto "dónde voy en la tarea" que el sistema actualice paso a paso. Eso no es un defecto: el RAG de una pasada es el diseño correcto cuando solo hace falta consultar el corpus.

¿Cuándo aporta un agente?

PedidoMejor enfoque
"Según la documentación, ¿qué significa este campo?"RAG
Pregunta fuera del corpus / sin evidenciaRAG + abstenerse (no inventar)
"Arma un plan de tarde: cine o música, 3 h, zona centro"Agente
"Hola, ¿qué tal?"Chatbot / saludo
En resumen agente ≠ LLM con personalidad, ≠ chatbot con historial, ≠ RAG. Aporta cuando la tarea se descompone en subtareas, necesita recordar decisiones intermedias o (más adelante) coordinar varias tools. El RAG puede ser una tool del agente más adelante.

La arquitectura mínima de un agente son cinco piezas y un bucle. Nada de frameworks todavía.

El bucle en Python

def run_agent(pedido):
    estado = inicial(pedido)
    while not parado:
        propuesta = LLM(estado)
        estado = actualizar(estado, propuesta)
        if objetivo_cumplido or límite:
            parado = True
    return estado

One-shot (RAG) vs multi-paso (agente)

🎯 One-shot

entrada → [pipeline fijo] → salida
          recuperar→prompt→generar

Una ejecución por pregunta. Ideal cuando basta consultar el corpus y responder.

🔁 Multi-paso

entrada → paso 1 → paso 2 → … → parada → salida
              └─ LLM actualiza el estado

Cada paso usa lo anterior. Por eso hace falta estado.

Ejemplo de tarea multi-paso "Quiero una tarde cultural de ~3 h: gratis o barato, cine y si no música en vivo, zona centro." El agente: (1) extrae preferencias → (2) propone 2–3 ideas → (3) ordena un mini-itinerario → (4) redacta el plan y marca que terminó. Cada paso consume tokens: sin límites, "funciona en la demo" y falla cuando el modelo se enrolla.
3

Estado y memoria del agente

El AgentState es la fuente de verdad del agente durante la corrida. El LLM sugiere cambios; tu código los valida y escribe. Es un contrato interno, igual que responder() → dict era el contrato externo en S10.

La forma del estado (dominio tarde cultural)

{
    "objetivo": "Planificar una tarde cultural",
    "pedido_original": "Quiero una tarde cultural.",
    "preferencias": {"intereses": [...], "presupuesto": ..., "zona": ..., "duracion_horas": ...},
    "plan": [],          # ítems del plan (vacío hasta poder cerrar)
    "respuesta": "",     # último texto para el usuario
    "done": False,       # lo calcula PYTHON, no el LLM
}

Tres reglas de diseño

Nombres estables

El prompt y el código deben hablar el mismo idioma.

El LLM no "es" la memoria

Si no lo escribes en el estado, en el siguiente turno se pierde.

done lo decide el código

El LLM rellena preferencias, plan y respuesta; Python calcula done.

Tres capas de memoria (no confundir)

CapaQué esDónde vive¿Persiste entre días?
A · Historial de chat (UI)Mensajes para pintar la conversaciónst.session_state.messagesNo
B · Estado de ejecuciónDónde va la tarea actualAgentState en el loopSolo durante la corrida (RAM)
C · Long-term memoryPreferencias / hechos entre sesionesExtra opcional: JSON en discoSí, si lo implementas
Frase del sprint messages pinta el chat; AgentState dirige la tarea.

Actualizar con estructura (JSON), no con prosa

Igual que en S10 pedías un JSON de respuesta, aquí pides un JSON de cambios de estado. Parsear lenguaje natural es frágil; el modelo devuelve datos y tu código los escribe.

{
  "preferencias": {"intereses": ["cine"], "presupuesto": "gratis_o_barato", "zona": null},
  "plan": [],
  "respuesta": "¿En qué zona te viene mejor?"
}
# El campo "done" NO viene del LLM: lo calcula Python.
El agente junior sólido: el LLM propone estructura; Python escribe el estado y decide done.
4

Flujos y control de ejecución

Un agente sin límites es un bucle caro. El agente debe dejar de aceptar mensajes por una razón explícita, dejar traza de lo que hizo y no tragarse los errores en silencio.

Condiciones de parada

CondiciónQuién la decideEjemplo
Objetivo cumplidoSolo códigocalcular_done: datos mínimos y len(plan) >= 2
max_turnsSolo códigoTope de mensajes; parar aunque done sea False
Error irrecuperableCódigoJSON inválido; API key ausente
Sin progreso (opcional)CódigoEstado idéntico dos turnos seguidos
max_turns es obligatorio Nunca confíes solo en que el modelo "cierre" la conversación con palabras. Quien llama a procesar_turno (CLI o Streamlit) controla el tope. Parar es una feature, no un fallo: un agente que se detiene con un plan parcial y un mensaje claro es mejor que uno que gasta 30 llamadas.

Errores y traza (una entrada por turno)

traza = [
  {"turno": 1, "mensaje": "Quiero una tarde cultural.", "status": "ok", "done": False},
  {"turno": 2, "mensaje": "Cine o música, barato.", "status": "ok", "done": False},
  {"turno": 3, "mensaje": "Zona centro.", "status": "error", "detail": "..."},
]

Abortar vs reintentar

error de parseo → reintentar 1 vez ("SOLO JSON")
sigue fallando  → state["error"] + traza "error"
error de auth   → no reintentar; mensaje claro

Regla de oro

Si en la live review no puedes enseñar qué turnos dio el agente, el diseño aún no es demostrable. HITL ("¿apruebas esta acción?") llega más adelante en el módulo.

De CLI a Streamlit

Mismo mensaje que en S10: la UI es un cliente. El contrato del agente es una función pública; consola y web solo la llaman.

El contrato: procesar_turno

def procesar_turno(estado: dict, mensaje: str) -> dict:
    # un mensaje → LLM → actualizar_estado → calcular_done → traza
    # devuelve: objetivo, preferencias, plan, respuesta, done, error, traza
ClienteCómo llama
CLI demorun_demo(max_turns=…) — guion de varios turnos
CLI interactivoprocesar_turno(estado, input()) en bucle
Streamlit app.pyTras cada chat_input: procesar_turno(agent_state, prompt)
❌ Anti-patrón
Copiar la llamada a Gemini dentro de app.py. Duplicas lógica, te saltas la traza y los límites, y rompes el contrato único.
✅ Correcto
estado = procesar_turno(st.session_state.agent_state, prompt) → guardas el estado y pintas estado["respuesta"].
La diferencia clave con S10 Además de messages, guardas agent_state en st.session_state para que el estado de la tarea persista entre mensajes. Si mañana cambias Streamlit por una API, procesar_turno no se toca: solo cambias el cliente.
6

El pipeline modular clave del sprint

La lógica del agente vive en un paquete src/ con tres módulos de una sola responsabilidad; arriba, dos clientes (CLI y app) que solo llaman al contrato procesar_turno. Vamos despacio.

La idea en una frase El LLM propone; Python decide; los clientes solo consumen. llm.py pide datos al modelo, state.py escribe el estado y calcula done, agent.py orquesta el turno con su traza. main.py y app.py no saben cómo funciona el agente: solo llaman a procesar_turno.

¿Por qué molestarse? (el problema que resuelve)

❌ Todo mezclado
Un script que llama a Gemini, parsea el JSON, decide si parar y pinta el chat, todo junto. El done lo "decide" el modelo, no controlas los turnos, y la web y la consola hacen cosas distintas. Imposible testear sin abrir el navegador.
✅ Una responsabilidad por archivo
llm habla con el modelo, state es la fuente de verdad, agent orquesta. Cambias el prompt o la regla de done en un sitio y ambos clientes se benefician. Pruebas el loop sin UI.

El proyecto por capas

🖥️ app.py  ·  🚪 main.py clientes (UI + CLI)
Dos caras del mismo agente. app: chat Streamlit con expander de debug. main: CLI con demo, --max-turns, --interactivo. Ninguno contiene lógica de agente: solo llaman a procesar_turno.
▼ ambos llaman a
🧠 src/agent.py orquestador · contrato
procesar_turno(estado, mensaje): llama al LLM → actualiza estado → calcula done → añade a la traza. Captura errores sin tumbar la app. run_demo() corre la demo con max_turns.
▼ usa dos piezas separadas
💬 src/llm.py habla con el modelo
Ensambla el prompt (instrucciones + estado + mensaje) y llama a Gemini. Devuelve un JSON de cambios (preferencias, plan, respuesta) — sin done.
▼ y
🗂️ src/state.py fuente de verdad
crear_estado, actualizar_estado (aplica el patch), calcular_done (Python decide) y leer_json. El estado nunca lo escribe el LLM directamente.
▼ parámetros
⚙️ config.py  ·  🔑 gemini_auth.py configuración
GEMINI_MODEL, MAX_TURNS_DEFAULT, TEMPERATURE, DEMO_MENSAJES. gemini_auth carga la API key una sola vez.

Qué hace exactamente cada archivo

src/state.py
Estado. Contrato del AgentState: crear_estado, actualizar_estado, tenemos_datos_minimos, calcular_done, leer_json.
src/llm.py
LLM. Prompt + llamada a Gemini → JSON de preferencias/plan/respuesta. No incluye done.
src/agent.py
Orquestación. procesar_turno (une LLM + estado + traza, captura errores) y run_demo (tope max_turns).
config.py
Configuración. Modelo, max_turns, temperatura y el guion DEMO_MENSAJES (5 turnos).
gemini_auth.py
Autenticación. Carga GEMINI_API_KEY desde .env (o la pide).
main.py
Cliente CLI. Demo, --max-turns, --interactivo. Imprime resumen + JSON con la traza.
app.py
Cliente Streamlit. Chat + sidebar + expander de debug. Guarda agent_state en session_state.

Cómo se hablan los módulos: los import

# src/agent.py — orquesta llm + state
from src.llm   import preguntar_al_modelo
from src.state import actualizar_estado, calcular_done, crear_estado

cambios = preguntar_al_modelo(estado, mensaje)  # llm.py → JSON sin "done"
estado  = actualizar_estado(estado, cambios)    # state.py escribe preferencias/plan
estado  = calcular_done(estado)               # state.py: PYTHON decide done

# main.py y app.py — solo conocen el contrato
from src.agent import procesar_turno
estado = procesar_turno(estado, mensaje)

Las dependencias fluyen en una sola dirección: los clientes se apoyan en agent, que se apoya en llm y state.

config.py · gemini_auth.py       # parámetros y clave
   ▲
state.py  ◄───►  llm.py          # fuente de verdad · habla con el modelo
       ▲         ▲
        agent.py                 # procesar_turno: orquesta el turno
           ▲
 main.py ◄─┴─► app.py            # CLI y web: solo consumen
Cómo explicarlo con tus palabras Piensa en un asesor de viajes: el LLM es el becario que propone ideas en una ficha (JSON), state es la carpeta oficial donde el jefe apunta lo confirmado y decide si el plan está cerrado (done), agent es el jefe que en cada turno pide la ficha, la pasa a limpio y anota en el registro (traza). La terminal y la web son dos ventanillas de atención que usan al mismo jefe.

El proyecto de la Live Review: agente de calidad del aire

La práctica integradora del sprint. Sobre este mismo patrón modular, tú implementas procesar_turno y run_demo en src/agent.py; el resto de archivos vienen dados. Dominio: aclarar una consulta sobre calidad del aire en Madrid y cerrar con un plan de consulta. Sin RAG ni tools, y sin inventar mediciones ni umbrales (no hay datos ni corpus).

Lo que implementas tú

  • src/agent.py → procesar_turno: un turno (LLM → actualizar_estado → calcular_done → traza, con manejo de error)
  • src/agent.py → run_demo: recorre DEMO_MENSAJES con tope max_turns

Lo que viene dado (no tocar)

  • src/state.py (crear / actualizar / calcular_done), src/llm.py (JSON sin done)
  • main.py, app.py, verificar.py, config.py, gemini_auth.py

El dominio: preferencias de la consulta

PreferenciaEjemplo
zonacentro, Escuelas Aguirre
contaminanteNO2, PM10, magnitud 83
tipo_consultaque_mide / interpretar / comparar / general
Regla de cierre done=true lo decide Python (calcular_done) cuando hay las tres preferencias y el plan tiene ≥2 ítems. El LLM nunca devuelve done.

Secuencia recomendada

CLI (arregla el backend primero)

python main.py               # demo de 5 mensajes (Fase 2)
python main.py --max-turns 2 # corte: solo 2 de 5
python main.py --check       # todo [OK] cuando termines

Web (app dada)

Checklist del sprint

Conceptos que debes dominar

  • Agente vs LLM / chatbot / asistente / RAG
  • El ciclo: loop + estado + parada + LLM
  • One-shot (RAG) vs multi-paso (agente)
