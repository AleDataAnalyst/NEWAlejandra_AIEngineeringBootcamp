ReAct con tools en LangGraph

ReAct = Reason + Act: el modelo razona si le faltan datos y actúa pidiendo una tool. Python la ejecuta y el resultado vuelve al modelo. El while de S12 ahora vive en dos nodos y una flecha que vuelve.

El grafo en una imagen

[START] → [agent] ──┬── ¿tool_calls? sí ──► [tools] ──► [agent]
                    │
                    └── no ──► [END]

LangGraph orquesta. No elige la tool ni decide cuándo parar: eso sigue en el modelo (la petición) y en Python (ejecución y tope).

Un turno, mensaje a mensaje

Pregunta: «¿cuánto es 3⁸?». Hay una tool calcular(expresion).

PasoQuiénQué se añade a messagesRouter
0CallerHumano: «¿cuánto es 3⁸?» · pasos=0→ agent
1agentModelo con tool_calls: calcular, {"expresion":"3**8"}→ tools
2toolsToolMessage("Resultado: 6561") · pasos=1→ agent
3agentTexto final: «3⁸ es 6561.»→ END

Piezas del grafo

📦 State

Lo que viaja entre nodos: lista de mensajes + contador pasos.

🧠 Nodo agent

Llama al LLM con bind_tools. Devuelve texto o tool_calls.

🧰 Nodo tools

Ejecuta lo que el modelo pidió y devuelve el texto de cada tool.

🔀 Router

Al salir de agent: si hay tool_calls → tools; si no → END.

↩️ Edge de vuelta

De tools a agent. Sin esta flecha el modelo no ve el resultado.

⏱️ Tope

pasos cuenta cuántas veces se entró en tools.

Estado y reducer

from typing import Annotated, TypedDict
from langgraph.graph.message import add_messages

class Estado(TypedDict):
    messages: Annotated[list, add_messages]   # se ACUMULA
    pasos: int                              # se SUSTITUYE

Qué hace add_messages

Un nodo devuelve solo el parche (return {"messages":[nuevo]}). El reducer añade ese mensaje a la lista existente. Sin él, se pisa.

Por qué messages y no otro nombre

El ToolNode preconstruido busca esa clave. Otros campos (pasos, plan, traza) viven en el mismo TypedDict.

Declarar una tool con @tool

from langchain_core.tools import tool

@tool
def calcular(expresion: str) -> str:
    """Evalúa una expresión matemática sencilla. Ejemplo: '3 ** 8'."""
    return f"Resultado: {eval_seguro(expresion)}"

tools = [calcular, obtener_clima]
llm_con_tools = llm.bind_tools(tools)

El modelo lee nombre + args + docstring. Una llamada no es ejecución: es un dict {"id","name","args"}. El nodo tools responde con un ToolMessage(content=..., tool_call_id="call_1"). Si el id no coincide, el modelo no sabe a qué petición corresponde el resultado.

Nodo agent

def nodo_agent(estado: Estado) -> dict:
    ai = llm_con_tools.invoke(estado["messages"])
    return {"messages": [ai]}

Nodo tools: dos estilos

EstiloQué hace
ToolNode(tools)Lee las llamadas del último mensaje y ejecuta las funciones @tool por ti.
Código tuyoUn for que ejecuta vía ejecutar_tool, con allowlist y validación.
 
from langgraph.prebuilt import ToolNode

def nodo_tools(estado: Estado) -> dict:
    salida = ToolNode(tools).invoke(estado)
    return {
        "messages": salida["messages"],
        "pasos": int(estado.get("pasos") or 0) + 1,   # ToolNode no cuenta
    }

Router + montaje

from typing import Literal
MAX_STEPS = 6

def router(estado: Estado) -> Literal["tools", "__end__"]:
    if int(estado.get("pasos") or 0) >= MAX_STEPS:
        return "__end__"
    ultimo = estado["messages"][-1]
    if getattr(ultimo, "tool_calls", None):
        return "tools"
    return "__end__"

grafo = StateGraph(Estado)
grafo.add_node("agent", nodo_agent)
grafo.add_node("tools", nodo_tools)
grafo.add_edge(START, "agent")
grafo.add_conditional_edges("agent", router)
grafo.add_edge("tools", "agent")     # ← vuelta fija
app = grafo.compile()

Cómo para el grafo

SeñalQuién la mira
El último mensaje no tiene tool_callsRouter → END. Hay respuesta.
pasos >= MAX_STEPSPython, en el router, antes de obedecer otro tool_calls.
recursion_limitLangGraph, si un bucle supera el tope del runtime.
No hace falta una tool marcar_done. El fin es "el modelo ya escribió texto" o "se acabó el cupo de pasos".

Errores típicos

  • Devolver el historial entero teniendo add_messages: cada mensaje se duplica.
  • Quitar add_messages: el parche pisa la lista y se pierde la pregunta.
  • Olvidar pasos: el modelo puede pedir tools en bucle.
  • Ejecutar la tool dentro de agent: se mezclan decisión y ejecución.
  • ToolMessage sin tool_call_id: el modelo no casa resultado con pedido.
  • Una flecha tools → END: el resultado no vuelve al modelo.

Migración desde el Sprint 12

En S12 el ciclo de tools era un while en Python (run_tool_loop). Aquí cambia quién encadena los pasos. Hay dos destinos; no son el mismo grafo.

S12   run_tool_loop  (while)
        │
        ├── destino 1   StateGraph ReAct       agent ↔ tools
        │
        └── destino 2   StateGraph supervisor  especialistas con for de tools por dentro

Destino 1 — el while pasa a nodos

Destino 2 — el producto (proyecto + Live Review)

El proyecto cultural y la Live Review de aire usan el mismo grafo: supervisor reparte el trabajo entre especialistas y un humano aprueba antes de cerrar. Cambia el dominio, no el dibujo.

Pieza del Sprint 12En el proyecto / Live Review

run_tool_loop como nodosNo es este grafo. El StateGraph es el supervisor.

Qué se añade alrededor S12 compilaba el grafo y se olvidaba al terminar el invoke. Ahora el checkpointer guarda el hilo, e interrupt_before para el grafo antes del nodo sensible. Sin checkpointer no hay dónde dejar esa pausa.

Persistencia, HITL y límites

Un invoke sin memoria empieza de cero. Y si no lo paras, corre hasta END aunque el siguiente paso sea sensible (cerrar un plan, reservar, publicar). Dos mecanismos cubren eso: checkpoints y human-in-the-loop.

Checkpoints y thread_id

invoke (turno 1) → foto del State
invoke (turno 2, mismo thread_id) → parte de esa foto
invoke (otro thread_id) → hilo vacío
from langgraph.checkpoint.memory import MemorySaver

app = grafo.compile(checkpointer=MemorySaver())
config = {"configurable": {"thread_id": "hilo-1"}}

app.invoke({"messages": [primer_mensaje]}, config)
app.invoke({"messages": [segundo_mensaje]}, config)

foto = app.get_state(config)   # no llama al modelo
# foto.values → State actual del hilo
# foto.next   → nodos que tocaría ejecutar (vacío si terminó)
ConceptoQué es
CheckpointFoto del State tras un paso del grafo.
thread_idIdentificador del hilo. Dos ids = dos conversaciones.
MemorySaverCheckpoints en RAM. Se pierden al cerrar el proceso.

Dos capas de memoria

CapaQué recuerdaCuándo
Reducer (add_messages)Acumula mensajes dentro del State de una corridaAl devolver un parche
CheckpointerEl State entre un invoke y el siguienteAl compilar con MemorySaver

Human-in-the-loop (HITL)

HITL es una pausa del grafo antes de un paso que no debe ocurrir solo: cerrar un plan, reservar, publicar. El modelo propone, una persona decide, el mismo hilo continúa.

START → [proponer] → (PAUSA) → [aplicar] → END
                      ↑
              interrupt_before=["aplicar"]
PiezaQué hace
Nodo proponerEl modelo escribe el plan. Deja aprobado=False.
interrupt_before=["aplicar"]El grafo no entra en aplicar hasta que alguien reanude.
Nodo aplicarLee aprobado. Cierra el plan o deja constancia del rechazo.
MemorySaverGuarda la foto de la pausa.
 
class EstadoPlan(TypedDict):
    pedido: str
    plan: str
    aprobado: bool     # lo escribe la persona, no el modelo
    resultado: str     # lo escribe aplicar, después de la pausa

app = grafo.compile(
    checkpointer=MemorySaver(),
    interrupt_before=["aplicar"],
)

Aprobar y rechazar

config = {"configurable": {"thread_id": "plan-1"}}
app.invoke({"pedido": "Tarde en Madrid…", "plan": "", "aprobado": False, "resultado": ""}, config)
foto = app.get_state(config)
# foto.next → ("aplicar",)   ← pausa

app.update_state(config, {"aprobado": True})
final = app.invoke(None, config)   # None = sin pedido nuevo, se reanuda
# final["resultado"] → plan cerrado
Aprobar y rechazar pasan por el mismo nodo aplicar. Cambia el booleano. La pausa no salta el nodo: impide entrar en él hasta que la persona haya escrito aprobado.

Quién escribe qué

QuiénQué escribe
Nodo proponer (modelo)plan
Quien llama al grafoaprobado, vía update_state
Nodo aplicar (Python)resultado

Límites en el grafo (siguen en Python)

LímiteDónde
Allowlist / validar argsEn la ejecución de la tool
Tope de toolsContador en el State o for con máximo
Tope de bucle de rolesContador de iteraciones en el router
doneUn nodo de Python, después de la pausa si la hay
Traza ok / error / blockedAl ejecutar cada tool

Errores típicos

  • Compilar con interrupt_before sin checkpointer.
  • Reanudar con otro thread_id: es otro hilo, no hay pausa que continuar.
  • Llamar a invoke con un mensaje nuevo cuando solo había que reanudar (invoke(None)).
  • Creer que rechazar se salta aplicar. El nodo corre igual; mira aprobado.
  • Dejar que el modelo escriba aprobado.

Multiagente: supervisor y especialistas clave del sprint

Un solo nodo con un solo prompt acaba mezclando oficios. Un grafo multiagente parte el trabajo en roles: un supervisor elige el siguiente; cada especialista lee y escribe el estado compartido. El flujo vuelve al supervisor hasta una salida explícita (FINISH).

START → supervisor ──┬── especialista A ──┐
                     ├── especialista B ──┼──► supervisor → … → FINISH → END
                     └── sintetizar ──────┘
No son procesos en paralelo Son nodos del mismo grafo, con prompts distintos, unidos por el State. El bucle es "especialista → supervisor", no un while escondido.

Piezas

PiezaRol
Estado compartidoCanal: pedido, notas de cada rol, plan, siguiente, iteracion, log
SupervisorMira el estado y escribe el siguiente rol. No redacta el trabajo del especialista.
EspecialistaUn nodo, un oficio. Lee lo que necesita y escribe su campo.
RouterTraduce siguiente → nombre de nodo (add_conditional_edges).
VueltaEdge fijo de regreso al supervisor desde cada especialista.
FINISH + topeSalida explícita. El tope lo aplica Python si el modelo no cierra.

Estado compartido con reducer de acumulación en el log

import operator

class Estado(TypedDict):
    pedido: str
    notas_a: str
    notas_b: str
    plan: str
    siguiente: str        # "a" | "b" | "sintetizar" | "FINISH"
    iteracion: int
    log: Annotated[list, operator.add]   # acumula; siguiente/iteracion se sustituyen

Supervisor con regla de respaldo (Python)

MAX_ITER = 8

def nodo_supervisor(estado: Estado) -> dict:
    it = int(estado.get("iteracion") or 0) + 1
    if it >= MAX_ITER:
        return {"iteracion": it, "siguiente": "FINISH"}
    siguiente = pedir_al_modelo(estado)
    if siguiente not in {"a", "b", "sintetizar", "FINISH"}:
        siguiente = regla_de_respaldo(estado)   # fallback determinista
    return {"iteracion": it, "siguiente": siguiente, "log": [f"{it}: {siguiente}"]}

def router(estado: Estado) -> str:
    if estado["siguiente"] == "FINISH":
        return "__end__"
    return estado["siguiente"]

grafo.add_edge(START, "supervisor")
grafo.add_conditional_edges("supervisor", router)
grafo.add_edge("a", "supervisor")
grafo.add_edge("b", "supervisor")
grafo.add_edge("sintetizar", "supervisor")

Dónde encajan las tools (y HITL)

El especialista puede ser un nodo "simple" (solo texto) o llevar dentro el ciclo de tools: el modelo pide, Python ejecuta, con un máximo de vueltas. Ese ciclo no tiene por qué ser otro par de nodos agent / tools en el grafo de roles: el grafo de fuera sigue enrutando oficios.

El cierre sensible (publicar, dar el plan por bueno) puede ser un nodo posterior, con interrupt_before justo antes de ese nodo.

Cuándo usarlo (y cuándo no)

✅ Tiene sentido cuando los oficios se separan de verdad: uno mira fuentes, otro encaja restricciones, otro redacta el cierre. Cada uno con su prompt.
❌ Innecesario si no hay roles distintos. Partir en especialistas no arregla un estado pobre ni una allowlist floja.

Errores típicos

  • Supervisor que también escribe el plan: deja de ser enrutador y el estado se pisa.
  • Especialista que no vuelve al supervisor: el bucle no existe y nadie decide FINISH.
  • Sin tope de iteraciones: el modelo puede alternar roles sin cerrar.
  • Estado sin campos por rol: todos escriben en el mismo texto y no se sabe quién aportó qué.

El paquete langgraph-supervisor ya no se mantiene. El patrón de aquí es un StateGraph escrito a mano.

Multimodal: imagen + texto en un nodo

Multimodal = el modelo recibe más de un tipo de entrada en la misma llamada. Aquí: una imagen y una pregunta. La respuesta sigue siendo texto. LangGraph no "ve" la imagen: solo decide dónde ocurre la llamada.

START → leer_imagen → END
            │
            ▼
   bytes de la imagen + pregunta → modelo → State.respuesta

Estado

class EstadoVision(TypedDict):
    ruta_imagen: str
    pregunta: str
    respuesta: str

La imagen no hace falta guardarla en el State como bytes si el nodo puede abrir la ruta. El State se queda con la ruta, la pregunta y el texto.

Dentro del nodo (parts: bytes + texto)

from google import genai
from google.genai import types

def nodo_leer_imagen(estado: EstadoVision) -> dict:
    datos = open(estado["ruta_imagen"], "rb").read()
    mime = "image/png" if estado["ruta_imagen"].endswith(".png") else "image/jpeg"
    respuesta = cliente.models.generate_content(
        model=MODELO,
        contents=[types.Content(role="user", parts=[
            types.Part.from_bytes(data=datos, mime_type=mime),
            types.Part.from_text(text=estado["pregunta"]),
        ])],
    )
    return {"respuesta": respuesta.text}

Como tool

La misma llamada puede ser una función: entra una ruta (o una imagen fija) y sale un string. El modelo la pide; Python la ejecuta y devuelve texto al ciclo de tools. El grafo no necesita un nodo "visión" si esa tool ya deja el texto en los mensajes. Así se usa en la Live Review (describir_imagen).

Límites y errores

Límites

  • Una llamada imagen → texto. No hay pipeline de visión, ni vídeo.
  • MIME correcto (image/jpeg, image/png).
  • El modelo describe. No consulta un catálogo por imagen: eso sería otra tool.

Errores típicos

  • Mandar la ruta como texto y no los bytes.
  • Guardar la imagen entera en el historial del grafo en cada turno.
  • Tratar la descripción como un hecho de una base de datos: es texto a partir de píxeles.

Live Review: agente multiagente de calidad del aire

El hito del sprint. Un agente multiagente con LangGraph que orienta consultas de calidad del aire en Madrid. Un supervisor reparte el trabajo entre especialistas, los especialistas usan tools (incluida una multimodal describir_imagen) y un humano aprueba o rechaza el plan antes de cerrar (interrupt_before + checkpointer).

Flujo del grafo

START → supervisor ──┬── diagnostico ────┐
                     ├── practico ───────┼──► supervisor → …
                     └── sintetizar ─────┘
                                │
                   FINISH → aplicar (interrupt_before) → END

Flujo de un pedido (procesar_turno)

Usuario escribe un mensaje (+ thread_id)

Conceptos que debes dominar

  • Grafo ReAct: nodos agent / tools + router por tool_calls + edge de vuelta
  • Reducer add_messages vs sustitución (pasos)
  • @tool, bind_tools, ToolMessage(tool_call_id=...)
  • Checkpointer vs reducer: dos capas de memoria
