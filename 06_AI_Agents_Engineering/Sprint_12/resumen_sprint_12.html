Qué es una tool

Una tool es una función de Python que el agente puede invocar para obtener información o hacer algo que el modelo no debería fingir. El LLM no la ejecuta: solo dice "quiero hora_actual con estos args".

Por qué no "inventarla" en prosa

ToolPor qué hace falta una función real
hora_actualLa hora cambia; el modelo no tiene reloj fiable
RAG_buscar_en_guiaDebe salir del corpus, no de la memoria del LLM
API_consultar_eventos_madridEventos reales (o fallback local), no inventados

Otros ejemplos habituales en la industria: obtener_clima, buscar_wikipedia, enviar_email, traducir_texto.

Anatomía de una tool: un contrato en cuatro piezas

1 · Nombre

Identificador estable: hora_actual.

2 · Descripción

Cuándo usarla. El LLM lee esto para decidir.

3 · Parámetros

Schema JSON: tipos y obligatorios.

4 · Implementación

Código Python que tú controlas.

👀 Declaración (lo que ve el LLM)

name: hora_actual
description: "Devuelve la fecha y hora…"
parameters: {}   # sin args

⚙️ Implementación (lo que corre Python)

def hora_actual() -> str:
    return datetime.now()...
# → "2026-08-06T15:04:12"

Qué NO es una tool

❌ Teatro, no tool use
Un prompt largo ("actúa como si buscaras…") · pegar todo un PDF en el contexto y fingir "retrieval" · dejar que el modelo escriba done=True o invente URLs. Si no hay función real detrás, no hay tool use: hay teatro.

Function calling y ciclo

Function calling (o tool calling) es el mecanismo de la API del LLM para recibir la lista de tools, responder con una petición estructurada (nombre + args) en vez de solo texto, y recibir después el resultado para continuar. No es magia: es un protocolo.

El protocolo en cuatro pasos

🙋
Pedir
el LLM devuelve un function_call
→
⚙️
Ejecutar
Python corre la función (si está permitida)
→
👁️
Observar
el resultado vuelve al LLM
→
💬
Responder
texto final (o más tools)

El ciclo con un ejemplo

Usuario: "¿Qué hora es ahora?"
        │
        ▼
   [LLM + tools declaradas]
        │
        ├── function_call: hora_actual()
        │         ▼
        │   Python ejecuta hora_actual()  →  "2026-08-06T15:04:12"
        │         ▼
        └── [LLM ve el resultado]
                  ▼
            Texto final: "Son las 15:04…"

Puede haber varias vueltas (varias tools) antes del texto final. Por eso se limita con max_steps.

Manual vs automático

🤖 Automático (AFC del SDK)

El SDK de Gemini ejecuta las tools por su cuenta. Es un atajo cómodo, pero pierdes el sitio donde meter allowlist, validación, traza y max_steps.

🛠️ Manual (lo que hace el proyecto)

Detectas la petición → ejecutas en Python → devuelves con Part.from_function_response → vuelves a llamar al modelo con el historial. En src/llm.py el AFC va desactivado con disable=True.

Warning de AFC al ejecutar Puede aparecer "Direct use of automatic function calling (AFC) in Models.generate_content is not recommended…". No es un error de tu código: el proyecto hace el loop a mano a propósito. Se puede ignorar.

El historial que hay que encadenar

RolQué lleva
userInstrucciones + pregunta del humano
modelEl function_call (o el texto final)
toolEl resultado de Python (Part.from_function_response)

types.Content = un turno del historial (role + parts). types.Part = un trozo de ese turno (texto, function call o function response). Sin ese encadenamiento, el modelo "olvida" que pidió la tool.

Errores frecuentes

  • No devolver el resultado al modelo → se queda a medias o inventa.
  • Nombre distinto en la declaración y en la función Python → fallos silenciosos.
  • Meter dumps enormes como resultado de tool → ruido y coste; resume.
  • Confiar en el LLM para la hora sin tool → demos que "funcionan" pero mienten.

Integración de herramientas

Las tools no viven sueltas en el notebook: viven en módulos y se registran por nombre. El notebook (o el agente) importa y orquesta; los .py ejecutan.

El contrato de una tool en Python

def nombre_tool(arg1: str, arg2: int = 5) -> str:
    """Descripción clara."""
    ...
    return "texto corto para el LLM"

Control y seguridad de tools

El modelo puede pedir cualquier nombre de función que se le ocurra, con cualquier argumento, tantas veces como quiera. Tu código solo ejecuta lo registrado, con args saneados y un tope de vueltas, y deja traza de todo.

Allowlist + validación de args

Punto único de ejecución

def ejecutar_tool(nombre, args=None):
    if nombre not in TOOL_REGISTRY:
        return f"Error: tool '{nombre}' no está permitida."
    limpios = validar_args(nombre, args)
    try:
        return TOOL_REGISTRY[nombre](**limpios)
    except Exception as e:
        return f"Error al ejecutar {nombre}: {e}"

Qué sanea validar_args

  • hora_actual → ignora args extra (devuelve {})
  • RAG_buscar_en_guia → consulta como string; vacía → error
  • API_consultar_eventos_madrid → limite entero acotado a 1…10

Sin Pydantic en este sprint: validación explícita y corta.

¿Qué hago si la tool no está permitida? Lo habitual: devolver el error como function_response y seguir el loop; el LLM puede disculparse o continuar sin esa tool. Más estricto: subir estado["error"] y cortar. En el proyecto hay dos capas: la comprobación en run_tool_loop (marca blocked) y la de ejecutar_tool (última barrera).

Status de cada tool en la traza

statusSignificado
okTool permitida y respuesta sin prefijo Error
errorTool permitida pero falló (excepción o mensaje de error)
blockedNombre fuera del registro: no se ejecuta

LímiteQué cuentaDónde viveDefault

max_steps es obligatorio Sin él, un mal prompt puede quemar cuota del LLM en bucle. Igual que en S11: parar es una feature, no un fallo.

Errores de tool

  • No dejes que la excepción tumbe Streamlit sin captura.
  • Devuelve un string de error en la function response o rellena estado["error"].
  • Prefiere fallback (API → JSON local) antes de abortar.

La traza: un turno, varios steps

{
  "turno": 1,
  "mensaje": "Quiero una tarde cultural en Madrid…",
  "status": "ok",
  "done": false,
  "tools": [
    {"step": 1, "tool": "RAG_buscar_en_guia", "args": {"consulta": "museos gratis centro"},
     "status": "ok", "preview": "Según la guía, el primer domingo…"},
    {"step": 1, "tool": "hora_actual", "args": {},
     "status": "ok", "preview": "2026-08-19T18:30:00"}
  ]
}

Cómo leerla

En el step 1 el modelo pidió dos tools a la vez (es normal: las pide en paralelo). El agente las ejecutó y guardó un preview (recorte de ~160 caracteres). Después la Fase 2 rellenó preferencias / plan / respuesta. done: false = aún faltan datos o el plan no cumple las reglas.

La traza no va al LLM

Se guarda en el estado de Python para depurar (expander de Streamlit, JSON de la CLI) y para la Live Review. No se manda entera en cada prompt: es ruido y coste.

done sigue siendo de Python. Tras el loop de tools se sintetizan preferencias / plan y calcular_done decide: datos mínimos (intereses, presupuesto, zona) y plan con ≥2 actividades. No existe una tool marcar_done.

Fuera de alcance (a propósito): sandboxing del SO, OAuth de tools, defensa dura contra prompt injection. El mensaje del sprint: solo corro lo registrado y con args saneados.

El corazón: run_tool_loop (resumido)

historial = [Content(role="user", parts=[INSTRUCCIONES_TOOLS + mensaje])]

for step in range(1, max_steps + 1):
    response = client.models.generate_content(contents=historial, config=gen_config)
    llamadas = list(response.function_calls or [])
    if not llamadas:
        return response.text, traza                # texto final → fin de la Fase 1

    historial.append(response.candidates[0].content)   # [model] pide tool(s)
    for llamada in llamadas:
        if llamada.name not in TOOL_REGISTRY:
            resultado, status = "Error: … no está permitida.", "blocked"
        else:
            resultado = ejecutar_tool(llamada.name, llamada.args)
            status = "error" if resultado.startswith("Error") else "ok"
        traza.append({step, tool, args, status, preview})
    historial.append(Content(role="tool", parts=respuestas))   # [tool] resultados

return f"He parado por max_steps={limit}…", traza

LangGraph básico

En S11 viste el panorama (State / Node / Edge). Aquí conectas lo que acabas de programar a mano con el grafo y practicas la API en dos notebooks obligatorios, que se hacen después del proyecto con tools.

Tu loop de tools = este grafo

[START]
   │
   ▼
[llamar LLM]  ← nodo "agent"
   │
   ├── function_call ──► [ejecutar tool] ──► (vuelve al LLM)   ← nodo "tools"
   │
   └── texto / plan listo ──► [actualizar estado / done] ──► [END]

# El "¿hay tool calls?" es un edge condicional.
Misma idea, otro orquestador Decisión (LLM) ≠ ejecución (Python); el grafo solo orquesta. Si mañana te piden "pásalo a LangGraph", tu procesar_turno y tu loop de tools ya definen los nodos.

Los dos notebooks

📓 01 · Primer grafo (lineal)

[START] → normalizar → proponer → [END]

StateGraph con un estado TypedDict (pedido, pedido_limpio, borrador, listo), add_node, add_edge, compile() e invoke().

📓 02 · Condicionales (router)

                     ┌→ preferencias → END
[START] → clasificar ┼→ eventos      → END
                     ├→ horario      → END
                     └→ general      → END

Un nodo clasifica la intención; una función router elige la rama con add_conditional_edges. Las ramas aún no ejecutan tools: solo cambian el prompt.

La API en un vistazo (notebook 02)

from typing import TypedDict, Literal
from langgraph.graph import StateGraph, START, END

class EstadoRouter(TypedDict):
    pedido: str       # texto del usuario
    intencion: str    # la escribe "clasificar", la lee el router
    respuesta: str    # la escribe la rama elegida

def router(estado) -> Literal["preferencias", "eventos", "horario", "general"]:
    return estado["intencion"]            # nombre del siguiente nodo

grafo = StateGraph(EstadoRouter)
grafo.add_node("clasificar", nodo_clasificar)
grafo.add_node("preferencias", nodo_preferencias)   # … eventos, horario, general
grafo.add_edge(START, "clasificar")
grafo.add_conditional_edges("clasificar", router)   # path_map opcional si nombres coinciden
grafo.add_edge("preferencias", END)                  # … cada rama → END

app = grafo.compile()
final = app.invoke({"pedido": "Me gustan museos baratos cerca de Sol", "intencion": "", "respuesta": ""})

Sidebar con max_turns y max_steps; expander Estado / traza de tools. Si hay plan pero done=false, verás Plan (borrador). Con done=true el chat se cierra; «Nueva conversación» resetea chat y agent_state.

Requisitos: Python 3.10+ y GEMINI_API_KEY en .env.

Guion de chat sugerido

#EscribeQué mirar
1"Quiero una tarde cultural barata en el centro de Madrid."Pregunta o empieza a rellenar prefs; done=false
2"Consulta la guía y algún evento del catálogo."En la traza: RAG_buscar_en_guia y/o API_consultar_eventos_madrid
3"Propón un plan concreto con 2 o 3 actividades."Aparece plan (borrador o final)
4"Perfecto, adelante."Prefs + plan ≥2 → done=true

Usa frases cortas y acotadas. Para forzar tools en un solo mensaje (ideal con max_steps=1): "Tarde cultural barata en centro. Usa la guía RAG y la API de eventos y propón un plan." Evita monólogos, pedidos fuera de Madrid/guía o "haz lo que quieras".

Conceptos que debes dominar

  • Qué es una tool: nombre + descripción + parámetros + implementación
  • Function calling como protocolo: pedir → ejecutar → observar → responder
  • Roles del historial: user / model / tool
  • RAG como tool y API con fallback (resúmenes cortos, nunca dumps)
  • Allowlist, validar_args y status ok / error / blocked
  • max_steps ≠ max_turns; done sigue siendo de Python
  • Tu loop de tools = grafo agent ↔ tools con un edge condicional

Práctica con el proyecto

  • Un turno con ≥2 tools y sabes leer su traza
  • --max-steps 1 muestra el corte por steps
  • Ves Fuente: fallback sin red
  • Provocas un blocked quitando una tool del registro
